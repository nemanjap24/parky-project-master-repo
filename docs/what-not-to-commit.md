# What not to commit

This repository is shared on GitHub. Anything pushed there can be copied, cached, or indexed, and it stays in the git history even after a later commit deletes it. This guide applies to everyone who commits here, people and AI coding agents alike.

`.gitignore` already blocks most of the files below. It is a safety net, not a guarantee: `git add -f`, a renamed file, or a new output path can bypass it. Check what you stage.

## Never commit

### Secrets and credentials

- `.env` and any other file with real values (`.env.local`, `.envrc`, `*.secret`).
- `OLLAMA_API_KEY` or any other API key, token, password, or connection string, including database URLs with a password (`postgresql://user:password@...`).
- SSH keys, certificates, and private keys (`id_rsa`, `*.pem`, `*.key`).
- Secrets pasted into code, tests, fixtures, docs, notebooks, commit messages, or PR descriptions. Do not use them as "examples" either.

Put new configuration variables in `.env.example` with a placeholder value, and keep the real value only in your local `.env` or on the server.

### Generated data and scraper output

- `output/` and `scraper/output/`: JSONL observations, discovery manifests, and classification results.
- Rendered HTML and debug dumps of pages (`scraper/output/rendered/`).
- Database dumps and backups (`*.dump`, `*.sql.gz`, `backups/`).
- Training datasets and exported features (`*.parquet`, large `*.csv`).

This data is regenerated by running the scraper. It also grows every week and can contain operational details. Keep it in the agreed archive (for example the shared drive or the school server), not in git.

### Local environment and editor files

- Virtual environments: `.venv/`, `venv/`.
- Caches: `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`.
- Editor and OS files: `.idea/`, `.vscode/` with personal settings, `.DS_Store`, `Thumbs.db`.
- Local AI agent settings and scratch output: `.claude/settings.local.json`, `Claude outputs/`.

### Personal and team-internal material

- Presentations, meeting minutes, drafts, and chat exports, unless the team decides to publish them in `docs/`.
- Anything with personal data: names with contact details, email addresses, phone numbers, school login data.
- Data from pages that are not public, or that were reached by logging in.

### Large binary files

- Videos, archives (`*.zip`), large images, and Office files (`*.pptx`, `*.docx`, `*.xlsx`). Git keeps every version forever, so the repository grows with each change. Share them through the team drive instead.

## What is fine to commit

- Source code, tests, and documentation.
- `.env.example` with placeholders only.
- `config/kosik_categories.json` and other non-secret configuration.
- Test fixtures in `scraper/fixtures/`, but only after review. A rendered page must come from a public product page. Check it first for cookies, session ids, tokens, tracking ids tied to a person, or any personal data, and remove them.

## Before every commit

1. Run `git status` and check that every changed file belongs to this change.
2. Run `git diff --staged` and read what you are about to commit.
3. Stage files by name (`git add scraper/models.py`) instead of `git add .` or `git add -A` when unrelated files are lying around.
4. Never use `git add -f` to force a file that `.gitignore` blocks without asking the team first.
5. Run `pytest`.

A quick search of the staged changes for obvious secrets:

```bash
git diff --staged | grep -iE "api[_-]?key|token|secret|password|bearer"
```

An empty result does not prove that the change is safe. It only catches the most obvious mistakes.

## Rules for AI coding agents

- Follow this file in addition to `AGENTS.md`.
- Do not read, print, or copy `.env`. Do not put secret values into code, tests, logs, or output.
- Commit only files you changed for the current task, staged by name.
- Do not commit generated output, rendered HTML, or anything from `Claude outputs/`.
- Do not change `.gitignore` to make an ignored file committable.
- If a file you are about to commit might contain sensitive data, stop and ask the user.

## If something was committed by mistake

1. **A secret was pushed:** treat it as leaked. Revoke or rotate the key immediately, then tell the team. Deleting the file in a new commit is not enough, because the old value stays in the history and may already have been copied.
   - **`OLLAMA_API_KEY` cannot be rotated by the team.** The key is issued by the professor who supervises the project. If it leaks, tell the professor right away, so they can revoke it and issue a new one. Until then, assume anyone can use the key. A leak may also cut off classification for the whole team, which is one more reason to keep it out of git.
2. **A secret was committed but not pushed:** remove it from the commit (`git reset --soft HEAD~1`, fix the files, commit again). If you are not sure whether it was pushed, treat it as pushed: rotate it, or for `OLLAMA_API_KEY` tell the professor.
3. **Large or generated files were pushed:** remove them in a new commit and add the path to `.gitignore`. Rewriting history (for example with `git filter-repo`) is possible, but agree on it with the team first, because everyone has to re-clone or reset their copy.
